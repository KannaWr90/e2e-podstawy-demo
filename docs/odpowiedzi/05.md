# Ćwiczenie 05: odpowiedzi

Każdy z pięciu testów przechodził, a każdy sprawdzał mniej, niż obiecywał jego komentarz „Wymaganie”. Numery linii dotyczą wersji z gałęzi `main`. Numery pytań odnoszą się do `docs/lista-kontrolna-review.md`.

## 01-dodanie-do-koszyka.spec.ts

| | |
|---|---|
| Błąd 1 (linie 21–22) | Asercje sprawdzają wiersz produktu na liście i aktywny przycisk „Dodaj do koszyka”. Oba były widoczne już przed kliknięciem. Test przejdzie, nawet gdy dodawanie do koszyka nie działa. Pytanie 3. |
| Błąd 2 | Test zostawia balsam w koszyku konta `user`. Każde uruchomienie zwiększa ilość o 1, a inne testy koszyka widzą obcą pozycję. Pytanie 9. |
| Dlaczego to problem | Wymaganie mówi o efekcie w koszyku. Test nie zagląda do koszyka. |
| Poprawka | Sprawdzić, że przed akcją balsamu nie ma w koszyku. Po kliknięciu sprawdzić komunikat „Dodano do koszyka: Balsam do ciała”, wejść na `/koszyk` i sprawdzić ilość `1` w wierszu balsamu. Na końcu usunąć pozycję. |

Dowód: zakomentuj linię 18 (kliknięcie). Wersja z `main` nadal daje `1 passed`, poprawiona pada na komunikacie.

## 02-moje-zamowienia.spec.ts

| | |
|---|---|
| Błąd 1 (linie 16–19) | `page.waitForTimeout(3000)` i `isVisible()`. Test zawsze czeka 3 s, także gdy lista przyszła po 0,5 s. Gdy serwer odpowie po 3,1 s, `isVisible()` zwróci `false` od razu, bez czekania, i test padnie bez błędu w aplikacji. Pytanie 8. |
| Błąd 2 (linia 20) | `getByRole('cell', { name: 'Nowe' }).first()` bierze pierwszą komórkę „Nowe” w całej tabeli. Gdyby ZAM-1004 było anulowane, test i tak przejdzie, bo inne zamówienia mają status „Nowe”. Pytanie 7. |
| Dlaczego to problem | Test jest wolny, niestabilny i nie wiąże statusu z zamówieniem z wymagania. |
| Poprawka | Lokator wiersza `getByRole('row').filter({ hasText: 'ZAM-1004' })`, `await expect(wiersz).toBeVisible()` (czeka sam), status w tym wierszu: `wiersz.getByTestId('order-status')` z `toHaveText('Nowe')`. |

Dowód dla błędu 2: anuluj ZAM-1004 w panelu admina i uruchom test. Wersja z `main` przechodzi. Po teście `npm run db:reset`.

## 03-adres-walidacja.spec.ts

| | |
|---|---|
| Błąd 1 (linia 24) | `toContainText('Popraw błędy')` sprawdza ogólny komunikat na górze formularza. Pojawia się przy każdym błędzie, np. złym telefonie. Komunikatu „Kod pocztowy musi mieć format 00-000” z wymagania test nie sprawdza. Pytanie 5. |
| Błąd 2 (linia 25) | `toHaveClass('error')` sprawdza klasę CSS ramki, czyli wygląd. Zmiana stylu wywróci test, choć aplikacja działa. Pytanie 4. |
| Brak | Wymaganie mówi, że adres nie zostaje zapisany. Test tego nie sprawdza. Pytanie 2. |
| Poprawka | Dokładny komunikat przy polu (`getByText('Kod pocztowy musi mieć format 00-000')`), dokładny tekst podsumowania „Popraw błędy w formularzu (1).”, brak komunikatu sukcesu, a po ponownym otwarciu strony pole kodu bez wartości `00000`. |

Dowód dla błędu 1: zmień w teście telefon na `123`, a kod na poprawny `00-001`. Wersja z `main` nadal przechodzi.

## 04-admin-wyszukiwanie.spec.ts

| | |
|---|---|
| Błąd 1 (linia 18) | Selektor CSS `table tbody tr:nth-child(1) td:nth-child(1)`. Zależy od kolejności kolumn i wierszy. Dodanie kolumny przed „Numer” albo zmiana sortowania psuje test bez błędu w wyszukiwarce. `CLAUDE.md` zabrania selektorów CSS. Pytanie 6. |
| Błąd 2 | Wymaganie mówi „dokładnie jedno zamówienie”. Test sprawdza tylko pierwszy wiersz. Wynik z kilkoma wierszami, z ZAM-1005 na górze, też przejdzie. Pytanie 2. |
| Poprawka | Wiersze z danymi przez `getByRole('row').filter({ hasText: 'ZAM-' })`, `toHaveCount(1)`, napis „Znaleziono: 1”, numer w pierwszej komórce tego wiersza. |

## 05-zmiana-adresu.spec.ts

| | |
|---|---|
| Błąd 1 (linia 8) | Test loguje się jako `admin`, a wymaganie dotyczy klienta. Pytanie 10. |
| Błąd 2 | Test nie przywraca adresu i za każdym razem zapisuje te same dane. Po pierwszym przebiegu konto ma już „Kraków”. Od drugiego przebiegu asercje `toHaveValue` przejdą, nawet gdy zapis przestanie działać, bo pola pokazują stare, identyczne dane. Pytanie 9. |
| Brak | Kod pocztowy i telefon nie są sprawdzane wcale. |
| Poprawka | Konto `user`. Przed akcją sprawdzenie, że miasto nie jest „Kraków”. Po zapisie ponowne otwarcie `/konto/adres` i sprawdzenie czterech pól. Przywrócenie adresu startowego w `test.afterEach`, które działa także wtedy, gdy test padł w połowie. |

Dowód dla błędu 2: uruchom wersję z `main` i otwórz http://localhost:4100/konto/adres jako `admin`. Pola mają już „ul. Lipowa 7” i „Kraków”, więc przy każdym kolejnym przebiegu asercje z linii 21–22 widzą te same wartości, czy zapis zadziałał, czy nie.

## Uwaga o `--repeat-each`

Testy 01, 03 i 05 w poprawionej wersji używają jednego konta `user`. Kilka kopii tego samego testu uruchomionych równolegle (`--repeat-each=3`) przeszkadza sobie w koszyku i adresie. Powtórki uruchamiaj z `--workers=1`:
```powershell
npx playwright test tests/review --repeat-each=3 --workers=1
```
Oczekiwany wynik: `15 passed`.
